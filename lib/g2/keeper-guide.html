FOR OPERATORS · SOLANA DEVNET

The arcade has no server.

Every game here needs someone to press buttons that anyone is allowed to press: fetch the Pyth price at the moment a prediction was aimed at, put it on chain, move the game to its next state. The program does not care who does it. A machine that does it is called a keeper.

Right now two keepers are running. Both belong to the person who built this. That is a single point of failure wearing a costume, and this page exists to end it.

What a keeper actually does

Ten public instructions, and nothing else. Four on the evidence layer — capture the first admissible Pyth print for a target time, capture a conflicting one, finalize, expire — and six on the game — activate an entry, settle a final, void a pending entry, void an active shot, finalize a resolved void, forfeit. On-chain rules decide which of them is legal at any moment; the keeper only offers.

What a keeper cannot do

  • It cannot see your prediction. Direction and confidence are sealed as a hash. The keeper moves a game it cannot read.
  • It cannot reveal for you. Your secret never leaves your side. If you never reveal, the game voids and your stake comes back — the keeper cannot take it.
  • It cannot choose the price. The rule is the earliest Pyth print at or after your target time, and finalize takes the minimum of everything submitted. A keeper that submits a flattering price submits a losing candidate.
  • It cannot lock anyone out. A second keeper may always do the same step. Whoever lands first wins it.

What it pays

Every step that anyone may perform pays one bond unit to whoever performs it, out of the deposit the player made when sealing. On devnet today one unit is 50 000 lamports.

This was not always true. Until 10 September 2026 the only paid instruction was the one that ended a game — so a keeper earned for letting a game die and earned nothing for keeping it alive. The gradient pointed at neglect. It does not any more.

Read that total again before you fund anything. A keeper serving one player loses about 0.0024 SOL per game. On devnet that is play money and it does not matter. It is stated here because a page that showed you only the +45 000 would be lying by arrangement.

Almost all of it is one thing: rent that never comes back. Recording a captured price creates a permanent account costing 1 254 760 lamports, and there is no instruction that closes it — the game reads that account when it activates and when it settles, and the evidence layer has no working count of how many games still depend on it. So the capital is spent, not lent.

Why this is a volume problem, not a dead end

A target time is shared. The price at 14:05 is the same price for everyone who aimed at 14:05, so the first keeper to capture it pays for all of them, and every player after that costs two 5 000-lamport signatures and earns 90 000. Break-even is roughly 28 shots per target time. Below it an operator subsidises the arcade; above it an operator profits.

Today the arcade is nowhere near that. So: running a keeper right now is a contribution, not a business. If that is not what you came for, this is the honest moment to close the tab.

Why do it anyway

  • Devnet SOL is free from the faucet. The loss is measured in play money.
  • An arcade whose games only finish because one person's laptop is awake is not permissionless in any sense that matters. Every independent keeper makes that less true.
  • You keep your own journal — a signed, replayable record of every maintenance action you performed. Nobody has to take your word for it, and you do not have to take ours.

Run one

Node 20.18.0 or newer; Node 22 recommended. Use the committed lockfile.

git clone --single-branch --branch main https://github.com/3esign/ratchetx.git
cd ratchetx
npm ci --omit=dev

Read-only first

Dry-run is the default. It validates chain state and prints the next maintenance action, if any. It loads no key, signs nothing, sends nothing, writes no journal.

node ops/g2-crank/live.mjs \
  --rpc https://api.devnet.solana.com \
  --operator YOUR_PUBLIC_KEY

Then send

node ops/g2-crank/live.mjs \
  --rpc https://api.devnet.solana.com \
  --operator YOUR_PUBLIC_KEY \
  --keypair /path/to/your/operator.json \
  --journal /path/to/your/keeper.json \
  --send --watch

Generate that keypair on the machine that will use it. Do not copy a key between machines, do not keep one in a repository or a shared folder, and use an operator key that holds nothing you would miss. The journal records public maintenance transactions and game identities; it never holds a player secret.

Every run re-validates the devnet genesis, both program addresses, the deployed program accounts, and the economy, ruleset and evidence hashes against their real on-chain relationships. Choosing a different operator changes none of those pins. Full operator notes, including crash recovery and the exact safety bounds, are in PUBLIC_KEEPER.md ↗.

Who is running one today

LAPTOPThe author's machine, in Serbia. The original, and until today the only one.
FRANKFURTAn independent Linux server under systemd, with a key generated on that host. Added 10 September 2026.

Two machines belonging to one person, funded from one payer, watching one public RPC, is redundancy — not decentralisation. The honest word is used deliberately. The third keeper is the one that changes the sentence, and it is not ours to run.

What is still broken

The evidence rent above does not come back, and it should. The fix is a reference count in the evidence layer — a game holds the target it depends on and releases it when it ends, and the last release refunds whoever paid — so that the capital becomes a float instead of a fire. The program names this as work for a later generation, and it is not done. Until it is, mainnet economics for this arcade are unsettled, and saying otherwise would be a sales pitch.

Devnet only. Test credits, no payout, and the network is periodically reset — nothing here is permanent. The RCX token is a separate mainnet asset and is not distributed by any keeper.
